Mnemos demo controls

Mnemos runs on a Google Cloud VM that is switched off by default and started only when you need it, for an interview or a demo. Everything here runs from one folder on this laptop: ~/Desktop/mnemos-demo.

Start here, every time 
cd ~/Desktop/mnemos-demo
./init

./init checks that you're logged in to Google Cloud (it opens the browser to log you in if not), confirms it can reach the VM, and prints the list of commands.

Interview day in five steps

1 · 30 min before
./init

Log in if asked. Confirms everything is reachable.

2
./up

Starts the VM and waits until the site works. Takes 3–10 minutes.

3
open the link

mnemos.harsha2803.dev: sign in once to warm it up.

4 · if it runs long
./extend 2

The VM switches itself off 4 h after starting. This moves that time.

5 · when done
./down

Stops the VM so you stop paying for it.

From your phone (no laptop)

The VM points the web addresses at itself when it starts and removes them when it stops, so the Google Cloud console's Start and Stop buttons do the same as ./up and ./down.

Checks your setup, logs you in if needed, and lists all commands.

Use it when
You open this folder after a while, or anything says "not logged in".
What happens
Checks gcloud is installed. If your Google login for cheellasreeharsha2803@gmail.com has expired, runs gcloud auth login and a browser tab opens. Then confirms the VM is reachable, checks the mnemos-demo SSH entry that Cursor uses, and prints the menu.
./upstarts billing · ~₹13 per hour

Turns Mnemos on and tells you when it's ready.

Use it when
Before an interview or demo.
What happens
Starts the VM, which gets a new IP each time. Points all four web addresses at that IP. Waits until the app reports "ready", printing dots, then shows the link.
Takes
3–10 minutes. The AI model has to load, so start it before the call, not during.
If it fails
"Not ready after 10 minutes": run ./status, then ./logs to see which part is stuck.

./downstops billing

Turns Mnemos off.

Use it when
You're finished. Always, even if the VM already switched itself off.
What happens
First removes the four web addresses, so they never point at an IP Google may give to someone else. Then stops the VM. Your data, the app and the AI model all stay on the disk, and the next ./up brings back exactly what was there.
Cost after
Only the disk, about ₹290 a month.

./extendsafe to looklonger time = more cost

Controls the automatic switch-off timer.

Every time the VM starts, it plans to switch itself off 4 hours later, so forgetting ./down can never cost more than a few hours.

TypeResult
./extendShows when it will switch off, in IST: "Powers off at Sat 26 Sep, 06:13 IST".
./extend 2Switch off 2 hours from now. Any whole number of hours works.
./extend offCancels the timer. It then runs and bills until you run ./down.
./sshno cost by itself

Opens a terminal on the VM.

Use it when
You want to look around on the server or fix something by hand. The app's code is in ~/mnemos.
Good to know
The VM has no public SSH port. This goes through Google's secure tunnel (IAP), so it works from anywhere once you're logged in. ssh mnemos-demo does the same.
Cursor
To edit on the VM in Cursor: Remote-SSH → connect to host mnemos-demo. The VM must be running (./up first).
./redeployVM must be up

Ships new code to the live demo, without you touching the VM.

Use it when
You merged a change into Mnemos on GitHub and want the demo to show it.
What happens
On the VM: pulls the latest code, rebuilds the containers, restarts them, clears the build cache (the disk is small), then waits until the app is ready again.
Variants
./redeploy updates the branch the VM is on. ./redeploy main switches the VM to main first. It refuses a branch that lacks the deploy files.
Takes
A few minutes. Don't run it during an interview.
./logsread-only

Shows the live logs of the running app. Ctrl+C to stop.

Use it when
Something in the demo doesn't work and you want to see why.
Variants
./logs shows every service. ./logs api shows one: api, web, worker, realtime, keycloak (sign-in), postgres, redis, rustfs (files), ollama (AI model).

Things that happen on their own

AutomaticWhy
Auto switch-off 4 h after every startA forgotten VM can't run up a bill. Change it with ./extend.
HTTPS certificate renewal (Let's Encrypt, free)Renewed while the VM runs and 10 minutes after each start. Valid 90 days at a time. ./status shows the expiry.
Web addresses follow the new IPThe VM points them at its new IP on every start and removes them on every stop (console, phone, ./down or the 4-hour timer). ./up and ./down also do it, which is harmless. The VM's service account mnemos-dns can edit only these DNS records, nothing else in the account.

If something goes wrong

You seeDo this
"Not logged in" / "Reauthentication required"./init, which logs you in again.
Site can't be reached./status. If the VM is TERMINATED or stopped, run ./up (or Start it from the phone). If the VM is running but the addresses show "(no record)", run ./up: it rewrites them.
"502 Bad Gateway"The server is up but the app isn't (yet). Wait a minute, then ./logs.
./up says "not ready after 10 minutes"./logs to find the failing part. ./ssh to look closer.
The VM switched off during a sessionThe 4-hour timer. ./up again, then ./extend 3.
Forgot to run ./downIt switched itself off anyway and removed the web addresses. ./status confirms; ./down is a safe extra clean-up.
Browser warns about the certificate./status shows the expiry. If it's past, ./ssh then sudo certbot renew.
