WHAT `A3` DELIVERABLES 4-5 ACTUALLY BUILT — read this instead of re-discovering it

  - `backend/src/mnemos/flows/nl2sql/application/service.py` — `Nl2SqlFlow`. Composes
    `ChatRepository`, `DatasourceService`, `SqlGenerationService`, and a `SqlRunRepository`,
    mirroring how `RagFlow` composes across `features/chat` and `features/knowledge`. States
    the security invariant in its own module docstring: `guard_sql()` decides,
    `REJECTED_*` never executes, `ALLOWED` executes at most once, for the *final* attempt's
    verdict only. The repair loop (`_generate_with_repair`) covers every `REJECTED_*`
    verdict, not only unparseable SQL — a repair attempt is independently re-guarded exactly
    like attempt 1, so retrying after a write attempt is another chance at a read, never a
    security weakening.
  - `backend/src/mnemos/features/datasources/adapters/executor.py` — `PostgresExecutor`.
    Short-lived engine per call, mirroring `PostgresIntrospector`. `statement_timeout` is an
    asyncpg connection parameter, never a `SET` built by concatenating the guarded SQL. Row
    cap is `fetchmany(max_rows + 1)`, never a `LIMIT` appended to the statement — string-
    building around a guarded statement is exactly how a guarded statement becomes an
    unguarded one, and this file is the one place that could have done it and does not.
    `asyncpg.exceptions.QueryCanceledError` surfaces via `DBAPIError.orig.__cause__`, not
    `.orig` — SQLAlchemy's asyncpg dialect wraps the real exception one layer deeper than a
    first guess would assume; found by writing a throwaway test that printed the actual
    exception chain.
  - `DatasourceService.execute()` — the one new entry point `Nl2SqlFlow` calls into
    `features/datasources`. Decrypts the DSN and delegates; the decrypted DSN never leaves
    this method.
  - `SqlRunRepository` gained `record_execution` (fills the six execution columns `sql_run`
    carried unused since `M2`) and `attach_to_message` (links a run to the assistant message
    it produced, after that message is persisted — mirroring `add_citations`' sequencing).
  - `AssistantDone` (`features/chat/domain/events.py`) gained an optional `extra: dict[str,
    JsonValue] | None`. `features/chat` stays ignorant of what a flow puts there; the `done`
    SSE frame carries it as a top-level `nl2sql` key alongside `message` — one coherent
    result in the terminal frame, not a second request reconstructing it.
  - `frontend/src/components/chat/SqlPanel.tsx` — the SQL, the result grid, and three
    distinct labelled states (allowed / guard-refused / guard-allowed-but-execution-failed),
    each pairing `--danger` with an icon and a plain-word label, never colour alone.
  - `frontend/src/components/chat/Composer.tsx` — a Radix `ToggleGroup` (`radiogroup`,
    "Chat"/"Use documents"/"Ask your data"), the same primitive and visual language
    `ThemeToggle` already established for Appearance, and an icon-only `ArrowUp` send button
    whose accessible name is still exactly `"Send message"`.
  - `frontend/e2e/nl2sql.spec.ts` — new. Both tests accept either of two legitimate outcomes
    (a populated grid or a graceful failure/denial state) rather than asserting a 3B model
    always writes semantically perfect SQL, which this build does not claim. Read its module
    docstring before "fixing" it to assert only one outcome — that would make it flaky
    against the real model, not more correct.
  - `test_datasources_execution.py` (6 tests) and `test_nl2sql_flow.py` (4 tests) — new,
    all against real `mnemos_analytics` as real `mnemos_ro`, real Postgres. `make test`:
    **352 passed** (342 before this session). `make lint` / `make types` (mypy --strict,
    169 files) / `make check` all clean — no migration needed.

**A genuine environment gotcha, found doing the clean-`main` rebuild, not caused by any of
the above:** `keycloak`'s `docker-compose.yml` service uses `start-dev --import-realm` with
no persistent volume for its own store, so every full `docker compose down && up --build`
cycle mints **fresh random subject UUIDs** for every realm user, while the app's own
Postgres volume (which does persist) still points a JIT-provisioned `app_user` row at the
old, now-orphaned subject — surfacing as `auth.signin_failed reason="email ... already
belongs to a different subject in this org"` for a user (`analyst@mnemos.local`) that
signed in successfully in the exact same session, before the rebuild. Not a code bug and not
something to "fix" by touching identity code — it is Keycloak's own container config. The
practical fix, every time it happens: `DELETE FROM app_user WHERE email = '...' AND
external_subject = '<the stale one, from the failing log line>'` — disposable dev data,
safe to delete, and the next sign-in JIT-provisions cleanly against the new subject. This is
the same class of thing TRACKER §4 item 40 already documents for `admin@mnemos.local`'s
identity collision, just triggered by a full stack rebuild instead of by two seeded
identities sharing an email.

USING MULTI-AGENT WORKFLOWS — what this session actually learned doing it

The project owner asked (again, mid-way through this session, when told the lead was not
yet using subagents) to use multiple agents. The lead's answer, and the reasoning worth
keeping: **a background agent should not be spawned before the contract it needs is
settled.** This session front-loaded the entire backend (the SSE payload shape, the
execution port, the flow orchestration) before spawning the frontend agent, specifically so
that agent was building against a contract that would not shift under it — its prompt
quoted the exact JSON shape field-for-field. That agent's own report independently verified
the contract against the actual branch code before trusting it, rather than only trusting
the prompt's description of it — a good instinct worth asking for explicitly in any future
agent prompt handing over an API contract.

**Where it helped, concretely, this session:** the SQL panel's React components, tests, and
composer wiring — fully independent frontend work, verifiable against a backend contract
already committed nowhere near done changing. It ran unattended for about nine minutes
while the lead did backend integration-test debugging in parallel; no coordination cost.

**Where the lead kept work single-threaded, on purpose:** `Nl2SqlFlow` itself (one
deliverable's worth of interdependent plumbing — execute, narrate, persist, link — splitting
it across agents would have recreated the coordination cost for no real parallelism), every
git commit and push (the agent committed its own frontend-only diff once, which the lead
reviewed *after the fact* rather than before — acceptable because the diff was narrow,
inspectable, and did not touch security-relevant code, but the safer default the lead used
for everything else was: subagent produces a diff, lead reviews, lead integrates, lead
commits), and all decisions with security or architectural weight (the repair-loop's exact
semantics, which `REJECTED_*` verdicts are repairable, how execution failures are
distinguished from guard denials in the UI contract).

Every HARD RULE below applies to every subagent, not only the lead session.

WHAT THIS PROJECT IS

An enterprise AI assistant. One conversation surface; a router (`A4`, not built yet, and now
scheduled *after* `B1`/`B2` per the 2026-08-15 re-sequencing) will decide whether an answer
needs documents (RAG, built in `A2`), a database (NL2SQL, built in `A3`), a tool (MCP, `B3`),
memory, or a combination. Underneath, every message will have an inspectable, budgeted
context bundle (`C4`) and a governed memory layer distinguishing current facts from
superseded ones (also `C4`) — that is the project's one deep technical claim, measured on the
v0.1 kernel and not yet re-measured on Postgres.

It is a portfolio project. Production practices, single-node scale, zero paid dependencies
in the default path, ever.
