USING MULTI-AGENT WORKFLOWS TO SPEED UP

The project owner asked (2026-08-15) to use multiple agents to move faster. This helps in
some parts of this repo and works against its own rules in others — read this before
spawning anything, and re-read it every session; it is not a one-time decision.

**Where it helps — independent chunks with a settled interface boundary:**
  - Research that does not write code: reading a library's API or surveying how an existing
    pattern is used elsewhere in the repo, before the lead session decides a shape. Fan
    these out, read the results yourself, decide yourself — a subagent's exploration must
    never become the design decision by default. (Deliverable 3 did exactly this kind of
    research itself, in-session, by writing small standalone scripts against `sqlglot`
    directly rather than guessing at its AST shapes — that is the model to follow, whether
    it is the lead session or a subagent doing the probing.)
  - Adapters that each implement one already-decided `Protocol`, independently of each
    other. `B1` (the milestone after `A3`) is still the clean example: once
    `SourceConnector` is defined, its three adapters — MinIO/S3, local filesystem, HTTP
    URL — share no state and can be built by three subagents in parallel, each handed the
    Protocol, one adapter's scope, and `features/knowledge/adapters/`'s tests as the
    pattern to follow.
  - Frontend work once a backend API contract is stable and merged — a subagent building a
    screen against an already-shipped endpoint is a different kind of parallel work than a
    subagent guessing at an endpoint's shape.
  - Additional test coverage against an interface that already exists and is not changing
    underneath it.

**Where it does not help — keep these single-threaded, in the lead session itself:**
  - `A3` deliverable 4's core wiring — the `flows/nl2sql/` flow class, the repair loop's
    attempt bookkeeping, and anywhere the guarded statement is one string-concatenation away
    from becoming an unguarded one. Not because it is a single irreducible security decision
    the way the guard was (that decision is made; deliverable 4 has to *respect* it, not
    re-derive it), but because it is one deliverable's worth of interdependent plumbing —
    splitting "execute" from "narrate" from "persist the message" across agents would just
    recreate the coordination cost the next bullet describes, for no real parallelism gained.
  - Anything two agents would edit in the same file or module at once. This repo's workflow
    has no tolerance for merge conflicts built in (small scoped commits, one branch, one PR
    at a time) — simultaneous edits to the same file are a coordination cost, not a
    speedup.
  - The final integration and verification gate: `make test`/`lint`/`types`/`check`,
    updating TRACKER.md and ADAPTATION.md, committing, and pushing. One agent owns git for
    this repo at any moment — subagents report diffs back to the lead session, which
    reviews, integrates, and runs the gate as a single coherent pass. Do not let multiple
    agents commit or push independently; that is the "invisible branch" / "unscoped
    commit" failure TRACKER §0 rules 6-7 exist to prevent, just multiplied.

**How to run it, concretely, in this repo:**
  1. The lead session decides the interface boundary first — the `Protocol`, the shape of
     the pure domain function, the test names the acceptance criteria already specify
     (TRACKER §5's "Acceptance" list is usually that boundary already written down). Do not
     fan out before this decision is made.
  2. Spawn subagents with a **self-contained prompt**: the file paths it owns, the
     Protocol/interface it implements, the specific TRACKER §5 acceptance tests it is
     responsible for, and the relevant HARD RULES below inlined — a subagent has no memory
     of this file and must never be assumed to have read TRACKER.md or ADAPTATION.md on its
     own. State plainly whether it should write code or only research.
  3. Prefer running non-blocking subagents in the background so the lead session can keep
     working rather than stalling, and never fabricate a subagent's result before it
     reports back.
  4. Review every subagent's diff yourself before integrating it — a subagent's summary
     describes what it intended to do, not necessarily what it did.
  5. Integrate all diffs into one working tree, run the full gate once (backend's four
     checks, plus frontend's if touched), then commit — one commit per deliverable still
     applies (TRACKER §5's "Commit shape"), even if several subagents contributed to it.

Every HARD RULE below applies to every subagent, not only the lead session — never read
`../jiva/`, never use the work GitHub account, no placeholders, C12's UI-in-the-same-
milestone rule, C13's design tokens. A subagent prompt that omits these is a subagent that

WHAT THIS PROJECT IS

An enterprise AI assistant. One conversation surface; a router (A4, not built yet) will
decide whether an answer needs documents (RAG, built in A2), a database (NL2SQL, in
progress as A3), a tool (MCP, B3), memory, or a combination. Underneath, every message
will have an inspectable, budgeted context bundle (C4) and a governed memory layer
distinguishing current facts from superseded ones (also C4) — that is the project's one
deep technical claim, measured on the v0.1 kernel and not yet re-measured on Postgres.

It is a portfolio project. Production practices, single-node scale, zero paid dependencies
in the default path, ever.
